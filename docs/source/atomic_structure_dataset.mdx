# Create an atomic structure dataset

There are two methods for creating and sharing an atomic structure dataset. This guide will show you how to:

* Create an atomic structure dataset from local files in python with [`Dataset.push_to_hub`]. This is an easy way that requires only a few steps in python.

* Create an atomic structure dataset with `PdbFolder` or `MmcifFolder` and some metadata. This is a no-code solution for quickly creating a dataset with several thousand structures.

Source paths and bytes are stored unchanged. Structures are read with AtomWorks only when a row is decoded; casting a column does not parse its files. Live atom arrays, RDKit molecules and ASE objects are serialized as BinaryCIF.

AtomicStructure currently requires the development atom-array IO API and Python 3.12 or newer. Published AtomWorks releases do not yet provide the required API. For development, install the tested checkout separately:

```sh
pip install "git+https://github.com/baker-laboratory/atomworks-dev.git@b84e6b48b0a2be9b468a3df3736e16e369e0fb70"
```

This repository currently requires access. Public CI and users without access must wait for the API's public release. The `bio` extra retains Biopython for the legacy features; it does not install this development dependency. Let AtomWorks install its exact Biotite dependency rather than independently selecting a Biotite version. Encoding file references and using `decode=False` do not need AtomWorks.

> [!TIP]
> You can control access to your dataset by requiring users to share their contact information first. Check out the [Gated datasets](https://huggingface.co/docs/hub/datasets-gated) guide for more information about how to enable this feature on the Hub.

## Local files

You can load your own dataset using the paths to your structure files. Use the [`~Dataset.cast_column`] function to take a column of file paths, and cast it to the [`AtomicStructure`] feature:

```py
>>> from datasets import Dataset, AtomicStructure

>>> structure_dataset = Dataset.from_dict({"structure": ["path/to/1abc.cif.gz", "path/to/ligand.sdf", "path/to/2xyz.pdb"]}).cast_column("structure", AtomicStructure())
>>> structure_dataset[0]["structure"]
<atomworks.io.utils.atom_array_plus.AtomArrayPlus ...>
```

mmCIF (`.cif`, `.mmcif`), BinaryCIF (`.bcif`), PDB (`.pdb`, `.ent`), MOL/SDF (`.mol`, `.sdf`) and Mol2 (`.mol2`) files are supported, optionally compressed with gzip, bz2 or zstd. RDKit `Mol`, ASE `Atoms` and biotite `AtomArray` objects can be used instead of paths.

By default decoding uses `atom_array_from_file` without chemical preparation: waters, hydrogens, crystallization aids, alternate conformers, insertion codes and original atom order are retained. CIF bonds are reconstructed during preparation, so do not assume that minimal loading provides a chemically prepared bond graph.

Pass `parse_config` to opt into preparation at **decode time**. Unspecified options use the minimal preset; for example `AtomicStructure(parse_config={"remove_waters": True})`. Presets such as `default` or `rcsb` opt into their full cleanup, including atom completion and filtering. `assembly` opts into building a biological assembly. These settings also apply to BinaryCIF inputs and can be changed with `cast_column` without rewriting stored data:

```py
>>> feature = AtomicStructure(parse_config={"preset": "rcsb"}, assembly="1")
>>> structure_dataset = Dataset.from_dict({"structure": ["path/to/1abc.cif.gz"]}).cast_column("structure", feature)
```

Then upload the dataset to the Hugging Face Hub using [`Dataset.push_to_hub`]:

```py
structure_dataset.push_to_hub("<username>/my_dataset")
```

This will create a dataset repository containing your atomic structure dataset:

```text
my_dataset/README.md
my_dataset/data/train-00000-of-00001.parquet
```

## PdbFolder and MmcifFolder

`PdbFolder` and `MmcifFolder` are dataset builders designed to quickly load a dataset with several thousand structure files without requiring you to write any code. `PdbFolder` reads `.pdb` and `.ent` files, `MmcifFolder` reads `.cif`, `.mmcif` and `.bcif` files.

> [!TIP]
> Take a look at the [Split pattern hierarchy](repository_structure#split-pattern-hierarchy) to learn more about how these builders create dataset splits based on your dataset repository structure.

They automatically infer the class labels of your dataset based on the directory name. Store your dataset in a directory structure like:

```text
folder/train/enzyme/1abc.pdb
folder/train/enzyme/2def.pdb

folder/train/receptor/3ghi.pdb
folder/train/receptor/4jkl.pdb
```

If the dataset follows the folder structure, then you can load it directly with [`load_dataset`]:

```py
>>> from datasets import load_dataset

>>> dataset = load_dataset("path/to/folder")
```

This is equivalent to passing `pdb` manually in [`load_dataset`] and the directory in `data_dir`:

```py
>>> dataset = load_dataset("pdb", data_dir="/path/to/folder")
```

If there is additional information you'd like to include about your dataset, like resolution or experimental method, add it as a `metadata.csv` file in your folder. You can also use a JSONL file `metadata.jsonl` or a Parquet file `metadata.parquet`.

```text
folder/train/metadata.csv
folder/train/1abc.pdb
folder/train/2def.pdb
```

Your `metadata.csv` file must have a `file_name` or `*_file_name` field which links structure files with their metadata:

```csv
file_name,resolution
1abc.pdb,2.5
2def.pdb,1.8
```

Here the `file_name` must be the name of the structure file next to the metadata file. More generally, it must be the relative path from the directory containing the metadata to the structure file.

Finally, [`~Dataset.push_to_hub`] the dataset to the Hub:

```py
>>> dataset.push_to_hub("<username>/my_dataset")
```

## Cost and preserving source data

Creating or casting a dataset of paths does no structure I/O. Byte inputs (including compressed files) are retained exactly. Saving or uploading embeds files without chemical preparation. Decoding pays the read cost for rows accessed; opt-in preparation adds its own per-read cost. AtomWorks' first import and CCD initialization may be expensive in each worker. Repeated reads repeat the work; for frequently reused prepared data, explicitly materialize it with `Dataset.map` after choosing your scientific preprocessing policy.

### Saving intentional edits

Decoded arrays retain their original encoding under `atoms.source_info["_hf_encoded"]`, so a pass-through `map` preserves source bytes and metadata. To save edits explicitly, use `materialize`. It serializes the atoms as supplied, ignores the retained bytes, leaves the input unchanged, and does no additional preparation:

```py
>>> feature = AtomicStructure()
>>> def translate(example):
...     atoms = example["structure"]
...     atoms.coord += [1.0, 0.0, 0.0]
...     return {"structure": feature.materialize(atoms)}
>>> edited = structure_dataset.map(
...     translate,
...     features=Features({**structure_dataset.features, "structure": AtomicStructure()}),
... )
```

The plain output feature avoids applying a previous cleanup policy or assembly expansion a second time. `materialize` also accepts stacks and nonempty lists of models with different atoms. The original dataset remains available; choose a separate output column or save location when both representations are needed.

### Preparing data once for training

Use `prepare_dataset` to apply a chosen policy once and store BinaryCIF for repeated access:

```py
>>> policy = AtomicStructure(parse_config={"remove_waters": True, "altloc": "first"})
>>> prepared = policy.prepare_dataset(
...     structure_dataset, "structure", cache_dir="prepared-cache", num_proc=2,
... )
>>> prepared.save_to_disk("training-structures")
```

The helper uses `Dataset.map`, preserves other columns and null rows, and returns an `AtomicStructure()` column. Reading it still parses BinaryCIF, but does not rerun cleanup or assembly generation. With no `cache_dir`, preparation is recomputed on every call.

A cache key includes source content hashes and paths, the dataset fingerprint, preparation/assembly settings, dependency versions, AtomWorks Python source, and this feature's implementation. Editable development changes therefore invalidate caches even when the package version is unchanged. Source files are read to check their content on every call; a hit avoids parsing and preparation, not file I/O. A miss reads files again and rejects changes detected between hashing and preparation. Embed private remote sources as bytes before using this helper.

Use `cache_version="my-ccd-v2"` for external scientific inputs such as custom CCD definitions, and change it when those inputs change. Such contexts must be reproducible in workers; use one process for in-process overrides. This cache is for the helper's preparation policy. Arbitrary custom transforms performed with `map` need their own correct fingerprinting and external-input versioning. Each process pays its own AtomWorks initialization and memory cost; start with one worker and measure before increasing `num_proc`.

### Serialization guarantees

| Input or property | Guarantee |
|---|---|
| Source file bytes, including compression | Preserved exactly until explicit materialization |
| Materialized coordinates | No deliberate coordinate rounding; float32 precision tested |
| Explicit bonds and periodic boxes | Stored in versioned BinaryCIF categories, including different models |
| Scalar per-atom annotations | Values tested for integers, floats, booleans and strings; inferred dtypes may change |
| Registered StandardAnnotations | Supported by the upstream writer; regression-tested |
| Arbitrary custom multidimensional, system-wide or pairwise annotations | Rejected explicitly |
| Integer annotations outside signed 32-bit range | Rejected explicitly |
| Empty models | Rejected by materialization; filter these rows before preparing storage |

CIF serialization can normalize author identifiers and annotation dtypes. It does not preserve all original file categories or custom Python objects; retain the original source dataset when that information matters. The versioned metadata reader still supports BinaryCIF written by the previous feature revision. These are format-specific guarantees, not a general arbitrary-array codec.

### Measuring your workload

`benchmarks/benchmark_atomic_structure.py` accepts local PDB/CIF files and reports cold first decode, repeated minimal/prepared reads, materialization cost, repeated BinaryCIF reads, and one/two-worker spawn throughput. It records input SHA256 hashes, dependency versions and peak process RSS. Run it with the same preparation policy, structure sizes and worker budget as your training pipeline. The script's default policy removes waters and selects the first alternate conformer; it is an explicit benchmark choice, not the feature default.

```sh
python benchmarks/benchmark_atomic_structure.py --files /data/*.cif.gz --output structures-benchmark.json
```

Peak RSS includes imports and CCD state and is a high-water mark, not incremental allocation. Worker peaks are reported separately and are not a simultaneous aggregate. The script does no downloads. Warm repeated reads may benefit from the operating system's file cache; network throughput is not measured. The prepared-byte read benchmark holds BinaryCIF in memory, while source reads include local file access and decompression. Measure saved Arrow reads separately for your training storage.

One local macOS/Python 3.12 run (three reads per entry, one native thread per worker) produced:

| PDB entry | Source atoms | Minimal source read | Source read + preparation | Materialized byte read |
|---|---:|---:|---:|---:|
| 1CRN | 327 | 2.83 ms | 16.20 ms | 2.25 ms |
| 4HHB | 4,779 | 20.77 ms | 40.72 ms | 17.28 ms |
| 6VXX | 23,694 | 98.82 ms | 219.34 ms | 79.00 ms |
| 6QNR | 305,753 | 2.124 s | 4.517 s | 1.330 s |

The 12-row minimal-decode batch took 8.27 s with one spawn worker and 5.78 s with two, including startup. Worker peak RSS was about 0.91–0.98 GiB; preparation/materialization cases peaked at 1.95–2.73 GiB including CCD state. Uncompressed materialized BinaryCIF was 1.39–2.50 times the compressed source size; this is not an equal-compression storage comparison. These four entries establish behavior across sizes, not a representative throughput estimate for the entire PDB. Raw measurements and source hashes are in `benchmarks/results/benchmark_atomic_structure.json`.

## Existing datasets and sequence records

`BioStructure` and `BioSequence` remain importable and registered, including their original serialized feature names and Biopython output types. Saved datasets continue to load. For new structure datasets prefer `AtomicStructure`; migrate an existing column explicitly with `cast_column("structure", AtomicStructure())`.

FASTA, FASTQ and GenBank keep their existing `record` columns and schemas. In particular, GenBank records retain sections such as REFERENCE and COMMENT that are absent from parsed columns. To avoid duplicate FASTA storage, choose `columns=["id", "description", "sequence"]` when loading. Changing sequence-loader defaults is separate from adopting AtomicStructure.
